# e2e-report-verification Specification

## Purpose

Define an automated end-to-end test that exercises the full Robot Framework -> `rf-allure` -> Allure report pipeline, verifies the generated report reflects the run, resolves an Allure CLI portably (with a graceful skip when unavailable), and is selectable via a registered `e2e` pytest marker.

## Requirements

### Requirement: End-to-end pipeline test

The project SHALL include an automated end-to-end test that, in one run, executes a Robot Framework suite to produce an `output.xml`, converts it with the installed `rf-allure` console script (invoked as a subprocess), generates an Allure HTML report from the produced results, and asserts the report exists and is well-formed.

#### Scenario: Full pipeline produces a report
- **WHEN** the end-to-end test runs with an available Allure generator
- **THEN** a Robot `output.xml` is produced, converted to an `allure-results` directory by `rf-allure`, and an Allure report directory is generated
- **AND** the report directory contains an `index.html` file

#### Scenario: Conversion is exercised through the packaged CLI
- **WHEN** the end-to-end test performs the conversion step
- **THEN** it invokes the `rf-allure` console-script entry point as a subprocess (not the in-process `generate` function), so the package's entry point is exercised

### Requirement: Report reflects the run

The end-to-end test SHALL use a representative suite covering passed, failed, and skipped tests (and broken tests when converted with the broken heuristic enabled), and SHALL assert, for each available generator, that the generated report's native statistics match the run and that one report test case exists per executed test. For Allure 2 the statistics SHALL be read from `widgets/summary.json` (`statistic`) and test cases counted in `data/test-cases/`; for Allure 3 (default single-plugin report) the statistics SHALL be read from `summary.json` (`stats`, treating absent status keys as zero) and test results counted in `data/test-results/`.

#### Scenario: Summary statistics match status counts
- **WHEN** an Allure 2 report is generated from a suite with known status counts
- **THEN** the counts in `widgets/summary.json` equal the known counts

#### Scenario: Summary statistics match status counts on Allure 3
- **WHEN** an Allure 3 report is generated from the same results
- **THEN** the counts in `summary.json` `stats` equal the known counts, with missing keys read as zero

#### Scenario: Every test appears in the report
- **WHEN** a report is generated by either generator
- **THEN** the generator's per-test data directory contains one entry per executed test

### Requirement: Portable Allure-CLI resolution with graceful skip

The end-to-end tests SHALL resolve Allure 2 and Allure 3 independently. Allure 2 SHALL be resolved from an `allure` executable on `PATH` that reports a 2.x version, else from `npx allure-commandline` when Node and Java are available. Allure 3 SHALL be resolved from an `allure` executable on `PATH` that reports a 3.x version, else from `npx allure` when Node is available. Each generator SHALL be invoked with its own command-line syntax. A generator that cannot be resolved SHALL cause its tests to be skipped; a generator that is resolved but exits non-zero or produces no report SHALL cause its tests to fail. Generator versions MAY be pinned through environment variables (`ALLURE2_VERSION`, `ALLURE3_VERSION`).

#### Scenario: Allure on PATH is used
- **WHEN** an `allure` executable on `PATH` reports version 3.x
- **THEN** it is used for the Allure 3 tests and not passed Allure 2-only options such as `--clean`

#### Scenario: Fallback to npx allure-commandline
- **WHEN** no `allure` executable is on `PATH` and Node and Java are available
- **THEN** Allure 2 runs via `npx allure-commandline` and Allure 3 runs via `npx allure`

#### Scenario: Graceful skip when unavailable
- **WHEN** a generator's prerequisites are not available
- **THEN** that generator's end-to-end tests are skipped rather than failing

#### Scenario: Resolved generator failure is not hidden
- **WHEN** a resolved generator exits non-zero or produces no `index.html`
- **THEN** the corresponding end-to-end test fails with the generator's error output

### Requirement: Selectable e2e marker

The end-to-end test SHALL be tagged with a registered `e2e` pytest marker so it can be included or excluded via `-m e2e` / `-m "not e2e"`, while still running by default and self-skipping when its prerequisites are unmet.

#### Scenario: Deselecting e2e tests
- **WHEN** pytest is run with `-m "not e2e"`
- **THEN** the end-to-end test is not collected and no marker-related warning is emitted

### Requirement: Capability coverage on both generators

The end-to-end tests SHALL, for each available generator, verify from the report data that: tag-derived labels (epic, feature, story, severity, owner, `allure.id`, plain tag) and links (issue, tms, link) are present; the test description is present; suite and test setup/teardown appear as fixtures; nested steps with `arg1..N` parameters are present; an embedded screenshot appears as an image attachment; a `Keyword Log` HTML attachment is present; and environment entries passed via `--environment` are listed.

#### Scenario: Capability suite on Allure 2
- **WHEN** the capability suite is converted and an Allure 2 report generated
- **THEN** every listed capability is found in the Allure 2 report data

#### Scenario: Capability suite on Allure 3
- **WHEN** the capability suite is converted and an Allure 3 report generated
- **THEN** every listed capability is found in the Allure 3 report data

### Requirement: Optional browser trace end-to-end test

The project SHALL include an end-to-end test, marked `browser`, that runs a robotframework-browser suite with tracing enabled (one per-test context and one suite-level context), converts it, and asserts that each trace is attached with the Playwright-trace MIME type and appears in both generators' report data. The test SHALL be skipped when robotframework-browser or its browsers are unavailable, and `browser` SHALL be a registered pytest marker.

#### Scenario: Browser traces end to end
- **WHEN** the browser test runs with robotframework-browser installed
- **THEN** both the per-test and the suite-level trace are attached and present in the generated reports

#### Scenario: Browser library unavailable
- **WHEN** robotframework-browser is not installed
- **THEN** the browser end-to-end test is skipped
